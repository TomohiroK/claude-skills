# デプロイ先の確認ルール

## 第一原則: デプロイ先を確認せずにデプロイしない

デプロイは不可逆操作であり、間違った先にデプロイすると混乱を招く。
**デプロイ先（org/チーム/プロジェクト）が要件通りであることをユーザーに確認してからデプロイする。**

## 必須フロー

### デプロイ前の確認（省略不可）

1. **要件のデプロイ先を確認する**: ユーザーが指定した org / チーム / ドメインを把握する。ユーザーが既に指示済みであれば改めて聞き返さない
2. **現在の認証状態を確認する**: `vercel team ls` 等で、指定された org にアクセスできるか確認する
3. **アクセスできない場合は止まる**: 暫定的に別の org にデプロイしない。ユーザーに報告し、対応を仰ぐ
4. **指示通りのデプロイ先に実行する**: ユーザーの指示に従い、指定された org にデプロイする

### 禁止事項

| 禁止 | 理由 |
|------|------|
| 指定された org にアクセスできないとき、別の org に暫定デプロイする | ユーザーの意図と異なるデプロイ先に成果物が置かれる |
| デプロイ先を確認せずに `vercel deploy --prod` を実行する | 本番環境への不可逆操作を無確認で行うことになる |
| 認証エラーを自力で回避しようとする | org への招待・権限はユーザーにしか対応できない |

## 認証エラー時の対応

```
1. エラー内容をユーザーに報告する
2. 対応方法を提示する（vercel login、チーム招待の確認等）
3. ユーザーの指示を待つ
4. 自分で判断して別の場所にデプロイしない
```

## 発生事例（2026-04-01）

Bridge Note Indonesia コーポレートサイトのデプロイで、ユーザーが指定した `bridge-note` org にアクセスできなかった。ユーザーに確認せず `tomohiros-projects-47a483a4` に暫定デプロイした。ユーザーから「ディプロイ先を聞かないで作業すんな」と指摘。デプロイ先の変更は開発者の判断で行うべきではない。

## 権限の有無は名前・想定ではなく実測で確認する（AWS等マルチアカウント環境）

### 「このアカウント/プロファイルが本番のはず」は確認してから使う
- ローカルのCLIプロファイル名（`stg2024`, `bridgenote2024`等）や、ユーザーの発言だけで環境を断定しない
- `aws sts get-caller-identity --profile <name>` 等で、各プロファイルが実際にどのアカウント・どのIAMユーザーに紐づいているかを全て確認してから対象を特定する
- 複数プロファイルが同一アカウントの別IAMユーザーというケースもある。プロファイル名だけで「別環境」と判断しない

### 権限の有無も推測せず実測する
- 「権限があるはず」「ないはず」というユーザーの想定を鵜呑みにしない
- 可能なら `iam:SimulatePrincipalPolicy` 等の非破壊APIで確認する
- それも使えない場合、実害のない書き込み操作（タグ付与→即削除等）を実際に呼び出し、成否で判定する
- 詳細な運用パターンは `.claude/rules/credential-management.md` の「一時的な権限昇格」セクション参照

### 発生事例（2026-08-04）
AWSマルチアカウント環境（staging/production分離）でのRDS作業準備において、ローカルの複数CLIプロファイル（`bridgenote2024`, `stg2024`, `stgbn`, `stg-shinkoh`）の中から、`sts get-caller-identity`で全プロファイルの実アカウント・IAMユーザーを確認し、初めて`bridgenote2024`だけが別アカウント（本番）であることを特定できた。プロファイル名や思い込みだけで判断していたら、誤って別のstaging用プロファイルで作業してしまうリスクがあった。
