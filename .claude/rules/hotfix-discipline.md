# ホットフィクス（本番バグ修正）の規律

## 第一原則: 修正の副作用を全コードパスでトレースする

ガード条件の追加・コードブロックの移動は、**そのメソッドの全呼び出し元**で期待動作を検証する。
「この呼び出し元は大丈夫だろう」と推測で省略しない。

## ガード条件追加時の必須チェック

### 全呼び出し元のトレース
メソッドにガード（早期 return）を追加する場合:
1. そのメソッドの全呼び出し元を grep で特定する
2. 各呼び出し元で、ガードが true/false になるケースを列挙する
3. ガードによって既存の正常フローが壊れないことを確認する

```
修正対象: _isIntegrate() にガード追加
  ↓
呼び出し元1: update() → ガードで false → OK（これが修正目的）
呼び出し元2: approval() → ガードで false → NG（承認時も会計連動しなくなる）
  ↓
対策: approval() では approval_at を事前セットしてガードを通過させる
```

### 条件式に使う変数の状態マトリクス
ガード条件に使う変数が、各呼び出し元でどの値を取るかをマトリクスで整理する:

| 呼び出し元 | $approvalSteps | $purchase['approval_at'] | ガード結果 | 期待 |
|-----------|---------------|------------------------|-----------|------|
| update() approver未設定 | null | empty | return false | OK |
| update() approver設定済 | 2 | empty | 通過 | OK |
| approval() approver未設定 | null | セット済み | 通過 | OK |
| approval() approver設定済 | 2 | セット済み | 通過 | OK |

## コードブロック移動時の変数依存チェック

### if ブロック内で定義される変数の追跡
コードブロックの順序を変更する際:
1. 移動するブロック内で**定義**される変数を全て洗い出す
2. それらの変数が移動先以降で**参照**されていないか確認する
3. 条件分岐（if）内で定義される変数は、分岐に入らなかった場合に未定義になることを認識する

```php
// 危険パターン: $ledgers_base は if 内でのみ定義
if ($this->_isIntegrate($purchase)) {
    $ledgers_base = ...;  // ここでのみ定義
}
// ... 後続で $ledgers_base を参照 → if に入らなかった場合 undefined
$purchase->accountterm_id = $ledgers_base['accountterm_id'];  // エラー
```

## PHP 緩い比較のトラップ

### null/false/0 が絡む比較は厳密比較（===）を使う
PHP の `==`/`!=` は型強制を行う。以下のトラップに注意:

| 式 | 結果 | 理由 |
|----|------|------|
| `null == 2` | false | null は 0 に変換 → 0 == 2 → false |
| `false != 2` | true | false は 0 に変換 → 0 != 2 → true |
| `null == 0` | true | null は 0 に変換 → 0 == 0 → true |
| `"" == 0` | true | "" は 0 に変換 → 0 == 0 → true |

ガード条件で `==`/`!=` を使う場合、入力値が `null`/`false`/`0`/`""` になるケースを必ずトレースする。

## エラー連鎖の根本原因特定

### 複数の症状が出たら根本原因を探す
1つのバグが複数の症状として現れることがある。各症状を個別に修正するのではなく、根本原因を特定する。

```
根本原因: _isIntegrate() のガード漏れ（自動承認）
  ↓
症状1: approval_status が勝手に 1 になる
症状2: 換算レートメッセージの誤表示（承認済み前提の条件判定）
症状3: 仕訳未作成（exchange_rate 判定ミスで integrated_status=0）
症状4: 承認取消エラー（accountterm_id が null で会計期間チェック失敗）
```

根本原因（症状1）を修正すれば、症状2-4は発生条件がなくなる。ただし、根本修正だけでなく各症状のガード（防御的プログラミング）も必要。

## HTML/JS/CSSの要素削除・改変時の影響分析

### ID・クラス・セレクタを削除する前に全参照箇所をgrepする
HTML要素（id, class）、CSS セレクタ、JS のDOM参照（`$('#xxx')`, `document.getElementById`）を削除・改変する場合、**変更前に**そのIDやクラス名をプロジェクト全体でgrepし、全参照箇所を特定する。

```bash
# 例: HTML要素を削除する前に、その要素IDの全参照を確認
grep -rn "alloc-client-dropdown" --include="*.js" --include="*.blade.php" --include="*.css"
```

### チェック対象
| 変更内容 | grepすべきもの |
|---------|---------------|
| HTML要素のid削除 | `#要素名` を JS, CSS, Blade 全体でgrep |
| HTML要素のclass削除 | `.クラス名` を JS, CSS, Blade 全体でgrep |
| data属性の削除 | `data-属性名` を JS, Blade 全体でgrep |
| JSイベントハンドラの削除 | そのイベントを発火させるHTML要素を確認 |
| CSS クラスの削除 | そのクラスを使っている HTML/JS を確認 |

### 禁止
- HTMLテンプレートを「書き直す」際に、既存の要素を影響分析なしで省略すること
- 「このIDは使っていないだろう」と推測で判断すること — grepで実証する

### クラウドインフラリソースへの一般化（WAF/IAM/セキュリティグループ等）

同じ原則はコードだけでなくクラウドインフラのリソースにも適用される。**WAF Classicのルール、IAMポリシー、セキュリティグループ等は複数の親リソース間で共有されることがある。** 削除・変更前に、対象がどの親リソースから参照されているか全て洗い出す。

```
例: WAF Classic の Rule/MatchSet はWebACL間で共有される
  ↓
Rule「prod-GEO」を含むWebACL一覧を確認する
  → demo-acl（削除予定） と prod-acl（保持予定）の両方が参照
  → 「demo-aclから参照を外す」のみ実施し、Rule自体は削除しない
```

- 削除対象のWebACL/ポリシー/リソース単体だけを見て「使われていない」と判断しない。共有されうる子リソース（Rule, MatchSet, ポリシードキュメント等）は、**全ての親からの参照が無くなって初めて削除可能**と判断する
- 実際にアタッチ先（ALB、API Gateway等）が存在するかをAPIで確認してから削除計画を立てる。「昔設定したから今は不要なはず」という推測だけで削除しない

### リージョナルリソースは「メインリージョンだけ確認」で終わらせない

WAF Classic/v2、ALB、EC2等のリージョナルリソースを棚卸しする際、**普段使っているメインリージョンだけを確認して「無い」と結論づけない**。同一アカウント内でも、過去の検証・移行作業等で他リージョンにリソースが残っていることがある。

- 課金情報（Cost Explorer等）にリージョン別の内訳が出ている場合、そこに記載された**全リージョン**を確認する。メインリージョン以外に課金が発生していれば、そこに未調査のリソースがある証拠
- 「このプロジェクトは`ap-southeast-1`しか使っていないはず」という思い込みで調査範囲を絞らない。既知の主要リージョン一覧（少なくとも該当サービスの主要リージョン）を機械的に洗う方が安全

#### 発生事例（2026-08-10）

staging AWSアカウントのWAFクリーンアップで、当初`ap-southeast-1`のみ確認し「WAFリソースは0件」と結論しかけた。ユーザーがCost Explorerで月額USD 8.00（us-east-1, us-east-2, us-west-1, us-west-2の4リージョンにそれぞれ$2ずつ）の請求を提示したことで見落としに気づいた。課金情報が示す4リージョンを追加確認したところ、各リージョンに1件ずつ未使用のWAFv2 WebACLが存在し、合計4件を削除して不要課金を解消した。

## 発生事例（2026-08-04）

本番AWSアカウントのWAF Classicクリーンアップで、削除対象と保持対象のWebACLが同じRule（`prod-GEO`）を共有していることが判明。事前に全WebACLのRule構成をAPIで取得し、共有関係をマッピングしてから削除順序を決定した。事前確認をせずに「不要なWebACLを一括削除」していた場合、保持対象（現役ALBにアタッチ中）が参照するRuleまで誤って削除する可能性があった。

## 発生事例（2026-04-11）

webfront2020 の開残按分モーダル（`_allocation_modal.blade.php`）を書き換えた際、`#alloc-client-dropdown` 要素を含めなかった。JSの `initAutocomplete()` がこの要素にドロップダウンを描画するため、クライアント検索が完全に動作しなくなった。テンプレート書き換え時にJSファイルからの参照をgrepしていれば防げた。

## 発生事例（2026-04-02）

webfront2020 の PurchaseController で `_isIntegrate()` にガードを追加。update() からの呼び出しは修正目的通りだったが、approval() からの呼び出しでもガードが効き、`$ledgers_base` が未定義になり本番で Whoops エラー。全呼び出し元のトレースを事前に行っていれば防げた。

## 発生事例（2026-04-09）

Career-Bridge jobseeker-front で `openingStaffRecruitment` フィルターのバグ修正中、`removePrefectureTag` で `hasSupportBonus: false` を明示的にセットしたことで新しいバグを作った。`false`（この属性を持たない求人で絞り込む）と `undefined`（フィルター未設定）は全く異なるセマンティクス。修正時は変更先の値のセマンティクスを必ず確認する。参照: `.claude/rules/whitelist-exhaustiveness.md`
