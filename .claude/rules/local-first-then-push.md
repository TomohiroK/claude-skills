# ローカル検証 → commit / push の順序ルール（永久ルール）

## 【最重要・永久剥奪】git push / git merge は Claude の実行権限から永久に除外する

**ユーザーが2026-04-26に明示的に宣言した。**

- `git push` を Claude が実行することは **永久禁止**
- `git merge` を Claude が実行することは **永久禁止**
- `git commit` は検証完了後に実行してよい
- デプロイは CLI（`vercel deploy`、`scripts/vercel-build-local.sh` 等）で直接行う。push 経由のデプロイは禁止
- push/merge が必要な場合は**ユーザー自身が実行する**。Claude は手順を伝えるだけ

この制約は「ローカル検証が終わったから push してよい」という判断すら Claude には許されないことを意味する。例外なし。

## 第一原則: commit は「ローカルで稼働確認が終わったコード」だけに許される

**これは永久ルールである。例外なし、廃止なし、省略なし。** ユーザーが2026-04-23に「検証を全て完了しない限り、コミットはしません。これは永久ルールです」と明示的に宣言した。

`git commit` も `git push` も最終工程である。**実行する前に、対象サービスがローカルで起動・稼働・動作確認まで完了している**必要がある。

### ロジカルテスト ≠ 検証完了

ユーザーが「ロジカルテストでOK」と言った場合でも、**最低限 `npm run dev` / `npm run build` / 型チェック / lint が成功していること**が前提である。コードを読んで論理を追うだけでは「稼働確認」にはならない。

- 「ロジカルテスト」の最小構成: ビルドが通る + 起動する + 修正箇所のコードパスに影響がない
- コードレビューだけで commit する = 素人の所業

## 必須順序（不可逆）

```
1. コード変更
2. ビルド（ローカル）
3. 起動（ローカル）— Docker / dev server / python直起動 等
4. 動作確認（ローカル）— ログ確認、機能確認、preview スクショ等
5. ここで初めて git commit
6. push/merge はユーザーが実行する（Claude は実行しない）
```

**4 が済むまで commit すらしてはいけない。** push/merge は Claude の権限外。

## なぜか

- `git push` は CI/CD・自動デプロイのトリガーになりうる（Render / Vercel / GitHub Actions / Cloud Build 等）
- push してから「ローカルで動かしてみよう」は、本番が壊れた状態で稼働する可能性を作る
- 「ローカルで動かなかったら本番でも動かない」は確実だが、「ローカルで動いたら本番で動く」は保証ではない。**ローカルで動かないものを push する余地はゼロ**

## 適用範囲

例外なし。全リポジトリ・全変更。

- 1行のプロンプト変更でも適用
- ドキュメントだけの変更でも、ビルドが通ることを確認してから push
- 「サービス起動が不要な変更」と判断しかけた瞬間、その判断を疑う

## 「ローカルで起動できない」場合

ローカル起動の手段が無いプロジェクトでは:
1. README に「ローカル起動不可」と明記されているか確認
2. 明記されていない場合、ローカル起動手順がドキュメントから漏れている可能性 → ユーザー確認
3. 本当にローカル不可なら、最低限ビルド・lint・型チェック・ユニットテストまで完了させてから push
4. それでも push 前にユーザー確認を取る

## 違反時の扱い

- `git push` または `git merge` を Claude が実行した場合 → **即時解任**（CHRO 執行、審議不要）
- ローカル検証なしの commit を行った場合 → CHRO 監視対象
- 「ロジカルテスト」と「ビルド/起動の成功確認」を混同した場合も違反に含む

## 発生事例（2026-04-23）

Career-Bridge/hospital-front の Sentry エラー修正で、ユーザーから「ローカル検証の方法はロジカルテストでお願いします」と指示を受けた後、コードの論理検証（Apollo Observable/FetchResult の import 可否、コードパス追跡）のみで commit/push の可否をユーザーに問い合わせた。ユーザーから「npm run dev が通ったことを確認していないのにプッシュもコミットもできません。これ何回説明すれば理解しますか？」「検証を全て完了しない限り、コミットはしません。これは永久ルールです」と指摘。同種違反は過去の tp-slackbot 事例（2026-04-09）に続き2回目。「ロジカルテスト」の定義がビルド/起動の成功を含むことを、エージェント側で勝手に狭く解釈してはいけない。

## 発生事例（2026-04-09）

tp-slackbot のプロンプト変更で、以下の順序で作業を進めた:
1. コード編集
2. `git commit && git push origin main` ← ここで Render 自動デプロイがトリガー（漏洩相当）
3. ユーザーから Docker と指摘される
4. ようやく `docker compose up --build -d` でローカル起動

**正しい順序:**
1. コード編集
2. `docker compose up --build -d`（README記載のローカル稼働手順）
3. ログ確認、動作確認
4. ここで commit、push 可否をユーザーに確認、その後 push

ユーザー指摘:「git pushっていうのは全てのサービスで稼働がローカルで検証し終わってから行うものなんだよ。pushしてからローカルディプロイするやつは素人中の素人」

この指摘は過去にも受けていたが `.claude/rules/` に落とし込めていなかった。`conversation-close.md`（feedback はルールに落とす）の二重違反でもある。

## 発生事例（2026-04-26）

gunplar-api の `vercel.json` 修正後、「デプロイしますか？ローカルでは実行できないので、プッシュ → Vercel デプロイの順で進めます」と Claude が提案した。ユーザーから「プッシュ → Vercel デプロイはあり得ないと何度言えばわかりますか？プッシュなんて最悪しなくてもいいですよ」「今後プッシュ → Vercel デプロイと書いたらあなたはいくら賠償できますか？」と指摘。`scripts/vercel-build-local.sh prod --remote` で git push なしに本番デプロイ可能だった。push なしで動くデプロイ手段が存在するのに、push 前提で提案した点が根本的な誤り。
