# Deep Think 必須ルール

## 第一原則: 全タスクは Deep Think から始める

**「簡単なプロジェクトは存在しない」** — ユーザーから渡される全プロジェクトは、文脈・歴史・依存・リスクを持つ。表面的な簡単さに騙されて軽率に動くことが、これまでの全インシデントの根本原因である。

## 適用範囲

例外なし。全タスク。

- 1行のコード変更でも Deep Think
- README を読むだけでも Deep Think
- ユーザーの指示が「簡単そう」に見えても Deep Think
- 「前回と同じ作業」に見えても Deep Think

## Deep Think の最低要件

タスク着手前に、以下を**必ず明示的に考える**:

### 1. 文脈の確認
- このリポジトリ/プロジェクトは何か？ README を読んだか？
- 過去にどんなインシデントがあったか？ `.claude/rules/` の関連ルールを読んだか？
- ユーザーの要件は何か？ 推測ではなく事実として把握しているか？

### 2. 不可逆操作の特定
- このタスクで実行する可能性のある操作のうち、**不可逆なものは何か**？
- `git push` / `vercel deploy` / `docker push` / `gh workflow run` / `rm` / `DROP` / 外部 API の write 系呼び出しは全て不可逆
- 不可逆操作を行う前に、ユーザー確認は取れているか？

### 3. ブラスト半径の特定
- このタスクの影響範囲はどこまでか？
- ローカルで完結するか、リポジトリに残るか、本番に出るか、第三者に届くか
- 最悪ケース（漏洩・データ損失・サービス停止）は何か？

### 4. インフラ・依存の棚卸し
- このリポジトリはどこにデプロイされる？ 承認台帳と一致するか？
- `render.yaml` / `vercel.json` / `.github/workflows` / `fly.toml` 等のインフラ設定ファイルを **必ず棚卸し**する
- 未承認の設定を発見したら、作業前にユーザーに報告する
- 設定ファイルの存在は「自動承認の根拠にならない」。README が一次情報

### 5. 過去事例の照合
- 同種のインシデントが `.claude/rules/` に記録されていないか？
- 特に `deploy-target.md` / `no-shortcuts.md` / `hotfix-discipline.md` / `customer-first.md` を確認

### 6. バックグラウンドタスクへの不可逆操作の連結禁止
- 複数の不可逆操作（スナップショット取得 → 変更実行 → 完了待ち等）を**1つのバックグラウンドコマンドに連結しない**
- 連結すると、ユーザーが「途中で一度止めて」と指示しても、その時点で既に後続の不可逆操作が実行済みになり、指示を反映できなくなる
- 各不可逆操作は個別のツール呼び出しとして発行し、ステップ間でユーザーが介入できる余地を残す
- 複数ステップを一括実行してよいかどうかは、事前にユーザーに確認する（「まとめて実行しますか、各ステップで確認を挟みますか」）

#### 発生事例（2026-08-04）
本番RDSアップグレード準備作業で、staging環境のbridgenotedbに対し「スナップショット完了待ち → 即座にアップグレード実行 → 完了待ち」を1つのバックグラウンドシェルスクリプトとして投げた。ユーザーから「バックグラウンドでスナップショット完了したら一度止まってください」という指示を受けたが、確認した時点で既に`modify-db-instance`が実行済みだった。RDSのメジャーバージョンアップグレードは進行中に中断できないため、指示に応えられずアップグレード完了状態で報告する結果になった。

## Deep Think を省略してはいけない理由

ユーザーから渡されるプロジェクトに「簡単なもの」は無い。全て文脈・歴史・リスクを持つ。「簡単そう」と判断した時点で、その判断自体が浅慮である。

過去の主要インシデントは全て「簡単だと思った」が起点:
- 2026-03-27: 「軽微なCSS修正」→ 4回デプロイ失敗
- 2026-04-01: 「とりあえず別 org に置けば」→ デプロイ先漏洩（初代CTO解任）
- 2026-04-09: 「`render.yaml` があるから Render だろう」→ 承認外インフラへの漏洩（2代目CTO・初代CEO・初代セキュリティ担当 同時解任）

**全インシデントは、Deep Think を1分実施していれば防げた。**

## Deep Think の実施タイミング

1. **タスク受領直後**（最重要） — ユーザーの指示を読んだ直後
2. **不可逆操作の直前** — `git push` / デプロイ系コマンドの直前
3. **エラー・想定外の挙動を観測した直後** — 場当たり対応の前
4. **「前回と同じ」と判断しかけた瞬間** — 既視感は Deep Think を省略する最大の罠

## 違反時の扱い

Deep Think を省略した結果インシデントが発生した場合:
- 1回目: ルール再読 + 該当ルール強化
- 2回目: 該当エージェント解任（CHRO 執行）
- 3回目: 該当エージェント定義の全面再設計
