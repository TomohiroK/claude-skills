# ホワイトリスト・列挙型の網羅性ルール

## 第一原則: フィールドを追加したら、全列挙箇所を更新する

コードベースにホワイトリスト（許可リスト）、列挙型、フィルターキーリスト等がある場合、新しいフィールドを追加した時点で **そのフィールドが列挙されるべき全箇所** を特定し、全て更新する。1箇所だけ直しても他が漏れていればバグは残る。

## 列挙箇所の特定手順（必須）

フィールド追加・修正時に以下を必ず実施する:

### 1. 同種フィールドを grep する
新しいフィールドと同種の既存フィールドを grep し、そのフィールドが登場する全箇所を列挙する。

```bash
# 例: openingStaffRecruitment を追加する場合、同種の hasSupportBonus を検索
grep -rn "hasSupportBonus" --include="*.tsx" --include="*.ts"
```

### 2. 全登場箇所で新フィールドの有無を確認する
同種フィールドが登場する全ファイル・全行で、新フィールドも同様に登場しているか確認する。

### 3. 不足箇所を全て修正する
1箇所ずつ修正してテストするのではなく、**全箇所を一括で修正してからテストする**。

## 典型的な列挙箇所（Webアプリのフィルター機能）

| # | 箇所 | 役割 | 漏れた場合の影響 |
|---|------|------|-----------------|
| 1 | 型定義（interface/type） | フィールドの存在定義 | コンパイルエラー（検出しやすい） |
| 2 | ホワイトリスト（VALID_KEYS等） | 許可するキーの制限 | フィルターが無視される |
| 3 | URL パラメータパース | URLからの復元 | ページリロードでフィルター消失 |
| 4 | URL パラメータ生成 | URLへの書き出し | 共有URLにフィルターが含まれない |
| 5 | localStorage 保存/復元 | 状態の永続化 | 画面遷移でフィルター消失 |
| 6 | boolean フィールド判定リスト | 文字列→boolean 変換 | "true" 文字列のまま処理される |
| 7 | アクティブフィルター判定 | 自動検索トリガー | フィルター設定しても検索が走らない |
| 8 | アクティブフィルター数カウント | UIバッジ表示 | フィルター数が実際より少なく表示 |
| 9 | フィルターリセット | 全解除機能 | リセットしてもフィルターが残る |
| 10 | サーバーコンポーネント | SSR時のフィルター適用 | SSRとCSRで結果が不一致 |

**新しいフィルターフィールドを追加する場合、上記10箇所全てを確認する。**

## boolean フィルターのセマンティクス

### `undefined` vs `false` vs `true` の3値を明確に区別する

| 値 | 意味 | APIリクエストでの扱い |
|----|------|---------------------|
| `undefined` | フィルター未設定（デフォルト） | キーを含めない |
| `true` | フィルターON（この条件で絞り込む） | `key: true` を送信 |
| `false` | フィルターOFF（この条件を**除外**する） | `key: false` を送信 → **意図しない絞り込み** |

### 禁止パターン
```typescript
// Bad: false を明示的に設定 → "この属性を持たない求人" で絞り込んでしまう
...(selectedFilter && { filter: true }),
...(!selectedFilter && { filter: false }),  // ← 危険

// Good: undefined で「フィルター未設定」を表現
filter: selectedFilter || undefined,
// true → true, false → undefined（キーが存在しない = フィルターなし）
```

### チェック方法
フィルターオブジェクトに `false` を明示的にセットしている箇所を grep し、それが意図的かを確認する:
```bash
grep -n "false" <filter-file> | grep -v "=== false" | grep -v "!="
```

## 「包括的テスト」の定義

**「包括的テスト」とは、全ファイルを横断して全データフローをトレースすることである。**

### 禁止: 単一ファイルテスト
1つのファイルだけチェックして「包括的テストを実施しました」と報告することは禁止。

### 必須: クロスファイルテスト
データの流れを上流から下流まで全て追跡する:
```
UI入力 → 状態管理 → localStorage → URLパラメータ → サーバーパース → APIリクエスト
```

各ステップで対象フィールドが正しく処理されているか確認する。

### 修正→テストのサイクル
1. 修正する
2. **全ファイル横断**のロジカルテストを実施する
3. バグが見つかったら修正する
4. **また全ファイル横断**のロジカルテストを実施する
5. 全テストPASSするまで繰り返す

**「修正したファイルだけ再テスト」は禁止。修正が他ファイルに影響を与えている可能性がある。**

## 発生事例（2026-04-09）

Career-Bridge jobseeker-front の `openingStaffRecruitment` フィルター:
- 東京都を選択すると `openingStaffRecruitment` フィルターが消える問題
- 根本原因: `SearchPageClient.tsx` の `VALID_FILTER_KEYS` ホワイトリストに `openingStaffRecruitment` が未登録
- 最初の「包括的テスト」は `SearchMenu.tsx` だけをチェックし、根本原因を見逃した
- 修正で `hasSupportBonus: false` を明示的にセットし、新しいバグを作った（`undefined` が正しい）
- 合計7箇所の修正が必要だった（ホワイトリスト、booleanFields、hasFilters、countActiveFilters、URLパラメータパース×2、URLパラメータ生成）
- 3ラウンドの修正→全ファイルテストサイクルで全バグを検出・修正
