# デバッグ・障害対応時の規律

## 第一原則: デバッグは推測探索ではなく、ユーザーの調査要点に従う

バグ原因調査・障害対応では、勝手に仮説を立てて関連しそうな箇所を広く探索しない。
ユーザーが具体的な調査要点（SQL、ファイル、関数、ログ行等）を出すので、それにのみ従って実行する。

## 禁止事項

- 調査要点が来る前に、自分の判断で migration / コード / deploy pipeline を横断的に推測調査すること
- 「念のため」投機的に migration・DB制約・インフラ設定を追加すること（本番相当DBを汚染するリスク）
- 指定された範囲外の「関連しそうな場所」に手を出すこと

## 正しい進め方

1. ユーザーから具体的な調査項目が来るまで待つ
2. 指定された範囲のみ調べて結果を報告する
3. 仮説を伝えたい場合は実行せず、「〜かもしれない。調べますか？」と選択肢として提示するに留める
4. 投機的な変更（migration追加等）は行わず、行った場合は追跡不能な drift を生む

## 発生事例（2026-04-21）

Career-Bridge の画像保存バグ調査で、migration/コード/deploy pipelineを横断的に推測調査した結果、投機的な migration（`20260420120002`）を追加して本番相当DB（staging）を汚染し、さらに削除してdriftを生じさせた。ユーザーから「デバッグに関してはお前素人すぎて使えない。こっちが調査要点を出すからそれに従え」と明言された。

## サイト疎通確認時: 自分のアクセスがブロックされている可能性を疑う

Claude自身のブラウザツールでサイトにアクセスして403/404等のエラーが出た場合、**サイト自体が壊れていると即断しない**。Cloudflare・さくらの「AIボット制限」等、AIエージェントのアクセスのみを選択的にブロックするセキュリティ機能が普及している。

**How to apply:**
- 自分のブラウザツールでエラーが出た場合、まずユーザー自身の通常ブラウザ（Chrome/Safari等）で同じURLにアクセスしてもらい、同じ結果になるか確認する
- 両方でエラーが出て初めて「サイト側の問題」と判断する。自分だけエラーなら、AIボット制限等のアクセス制御が原因の可能性が高い
- 管理パネルに「Webサイトアクセス制御」「AIボット制限」等の項目がないか確認する

### 発生事例（2026-08-06）
futureworks-inc.jp のWordPress移行作業で、Claudeのブラウザツールがトップページアクセス時に403を継続的に検知し、移行作業に失敗したと誤診断しかけた。実際にはさくらの「ウェブサイトアクセス制御」機能で「AIデータスクレイパー」制限が有効になっており、Claudeのアクセスだけがブロックされていた。ユーザー自身のブラウザでは正常に表示されており、サイト自体は正常に復旧していた。
